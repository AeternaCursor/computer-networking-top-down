# P0 · 观察网络：一次网页访问的完整解剖

> 对应章节：第 1 章（延迟、丢包、分层）。工具：Wireshark + 30 行 Python。

## 1. 现象：抓包看到什么

抓 `http://example.com`，一次网页访问 = 四步，全部肉眼可见：

| 步骤 | 抓到的包 | 内容 |
|---|---|---|
| 查号 | dns 一问一答 | `Standard query A example.com` → 2 个 IP（104.20.23.154 / 172.66.147.243，Cloudflare） |
| 握手 | SYN → SYN,ACK → ACK | 实际走了 IPv6（网络是 v4/v6 双栈） |
| 要货 | `GET / HTTP/1.1` → `200 OK` | 响应头 `Content-Type: text/html`、`Content-Length` |
| 挂电话 | FIN ×2 + ACK | 本轮抓包中因 keep-alive 未出现，连接被留着复用 |

另捕获：对 `140.82.114.3`（GitHub）的 SYN 成对出现 **Retransmission**——喊话没人应，1 秒后重发。

## 2. 矛盾：这些协议各解决什么问题

- **DNS**：人记名字，机器认 IP → 必须有翻译层
- **握手**：通话前不知道对方在不在 → 先双向确认，再传数据
- **重传**：网络不保证送达（尽力而为）→ 丢了就等 RTO≈1s 重发
- **HTTP 头**：一堆机器说同一种话 → 用结构化字段自描述（我是谁 Host、我要什么 GET、给你什么 Content-Type）

## 3. 设计：为什么是这样

- DNS 答案存本地缓存（小本本）→ 重复访问不再查号
- 握手耗时 = 一个来回（RTT），恰好可用作延迟探测的尺子
- RTO 初始值约 1s：太短会加重拥塞，太长干等浪费时间

## 4. 实现：rtt_probe.py

`socket.create_connection((host, port), timeout=3)` 内部自动完成 **DNS 查号 + SYN 三握**；前后 `perf_counter()` 掐表，差值即 RTT。异常分支 = 3 秒内 SYN 无应答（对应 Wireshark 里的纯重传场景）。

## 5. 验证：实测数据

```
百度（国内）:  111.8 / 24.6 / 17.6 / 10.6 / 24.3 ms
  → 第 1 次明显偏慢：计时里含 DNS 查号；后续命中本地 DNS 缓存，只剩握手
GitHub（国际）: 304.9 / 266.3 / 1308.9 / 283.4 / 1311.7 ms
  → 基线 RTT ≈ 270ms（距离税）
  → 1308 / 1311 ms ≈ 1s + 270ms：SYN 丢一次，干等 RTO(1s) 重发成功
复测一轮:     百度 27~62ms；GitHub 稳定 267~280ms（本轮未丢包）
```

三个结论：

1. **RTT 差 10 倍** = 路程远近，不是服务器性能
2. **1300ms ≈ RTO(1s) + RTT(0.27s)**：Wireshark 里"看到"的重传，被代码"量出"了时间——同一现象，两种证据
3. 生产日志 `Connection timed out` = SYN 无人应答（卡第一握）；`Connection refused` = 对方明确拒绝。病因不同，排障方向不同

## 6. 升华：对照书本与遗留

- 书上"四种延迟"中的**传播延迟**，实体就是这里的"距离税"；**排队/丢包**的后果就是 RTO 重传
- 丢包重传是运输层"可靠性"的伏笔：P4 将在 UDP 上手写停等/GBN/SR，亲手造这套机制
- 遗留（不阻塞 P1）：tracert 逐跳观察、精读 1.1~1.4、抓一次完整的 FIN 四次挥手
